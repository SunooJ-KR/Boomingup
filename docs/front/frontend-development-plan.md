# 프론트엔드 개발 플랜

> 작성: 2026-09-16
> 기준 문서: `docs/front/product-plan.md`, `docs/front/frontend-reproduce.md`
> 목적: 사용자 경험을 먼저 검증할 수 있는 순서로 프론트엔드 구현 범위와 화면 구조를 정리한다.

## 1. 개발 목표

첫 버전의 목표는 사용자가 법정동을 검색하고, 선택한 동의 12개월 추정 변화율과 사실정보를 한 화면에서 이해하는 것이다.
지도는 중요한 탐색 방식이지만, 법정동 경계 GeoJSON이 아직 없으므로 MVP의 필수 조건으로 두지 않는다.

| 구분 | 목표 |
|---|---|
| 핵심 경험 | 검색 → 목록 선택 → 동 상세 확인 |
| 핵심 정보 | 추정 변화율, 추정 구간, 최근 1년 거래 수, 서울·자치구 비교, 사실정보 |
| UX 원칙 | 예측을 과장하지 않고, 표본 수와 검증 한계를 같이 보여준다 |
| 1차 제외 | 매수 추천, 전체 랭킹 중심 화면, 세부 구간 예측, 자동 투자 성향 진단 |

## 2. 권장 기술 스택

`docs/front/frontend-reproduce.md`의 이식 가이드를 따른다.

```text
Next.js 15 App Router
React 19
TypeScript
Tailwind CSS v4
class-variance-authority
clsx
tailwind-merge
lucide-react
```

`front/`가 비어 있으므로 새 프로젝트를 만들 때는 위 조합으로 시작한다.
초기에는 정적 JSON 또는 서버 API 중 하나를 선택하되, UI 컴포넌트는 데이터 출처에 묶이지 않게 만든다.

## 3. 정보 구조

### 3.1 첫 화면

첫 화면은 지도보다 검색과 상세 이해를 우선한다.

```text
desktop:
  [검색·필터·목록] [선택 동 상세]

tablet:
  [검색·필터]
  [목록]
  [선택 동 상세]

mobile:
  [검색]
  [필터]
  [목록 카드]
  [상세 카드]
```

지도 데이터가 준비되면 desktop 구조를 다음처럼 확장한다.

```text
desktop:
  [검색·필터·목록] [지도] [선택 동 상세]
```

### 3.2 주요 화면 블록

| 블록 | 역할 | UX 기준 |
|---|---|---|
| 상단 헤더 | 서비스 이름, 기준 분기, 데이터 기준 안내 | 얇고 고정한다. 마케팅 문구를 길게 쓰지 않는다 |
| 검색·필터 | 자치구, 법정동, 예측 제공 여부, 지역 태그 필터 | 사용자가 바로 동을 찾게 한다. 첫 화면을 랭킹으로 시작하지 않는다 |
| 동 목록 | 검색 결과와 핵심 요약 | 변화율보다 상태, 거래 수, 구 이름을 같이 보여준다 |
| 예측 카드 | 추정 변화율과 구간 | "추정", "기준 분기", coverage 안내를 항상 붙인다 |
| 비교 카드 | 서울·자치구·법정동 흐름 비교 | 순위보다 맥락을 보여준다 |
| 사실정보 카드 | 전세, 공급, 정비사업, 규제 | 예측 이유처럼 보이지 않게 "관측 정보"로 표시한다 |
| 단지 목록 | 선택 동의 단지와 최근 거래 | 상세 화면 하단에 둔다. 첫 화면을 복잡하게 만들지 않는다 |

## 4. 데이터 계약

초기 프론트는 다음 세 층의 데이터를 기대한다.

| 데이터 | 용도 | 최소 필드 |
|---|---|---|
| 동 목록 | 검색, 필터, 목록 카드 | `dong_id`, `gu_name`, `umd_name`, `status`, `change_pct_est`, `lower_pct`, `upper_pct`, `n_sales_4q`, `tags` |
| 동 상세 | 선택 동 상세 화면 | `prediction`, `facts`, `comparison`, `complexes` |
| 메타 | 전체 화면 안내 | `as_of_quarter`, `data_period`, `horizon_months`, `interval_coverage_backtest` |

`docs/payload-schema.md`가 아직 초안이므로 프론트 구현 전에 다음 필드를 추가할지 합의한다.

| 추가 후보 | 이유 |
|---|---|
| `tags` | 규칙 기반 지역 유형 태그와 필터 구현 |
| `comparison.seoul_change_pct` | 서울 전체 흐름 비교 |
| `comparison.gu_change_pct` | 자치구 흐름 비교 |
| `comparison.dong_change_pct` | 선택 동 과거 흐름 비교 |
| `status_reason` | 예측 미제공 사유를 화면에 안정적으로 표시 |

## 5. 컴포넌트 설계

기본 UI는 `frontend-reproduce.md`의 primitive를 그대로 따른다.

| 컴포넌트 | 설명 |
|---|---|
| `Button` | 주요 행동과 필터 초기화 |
| `Card` | 예측, 비교, 사실정보, 단지 항목 |
| `Badge` | 예측 상태, 지역 태그, 규제 여부 |
| `Input` | 법정동·자치구 검색 |
| `SectionHeading` | 패널 단위 제목 |

도메인 컴포넌트는 다음처럼 나눈다.

| 컴포넌트 | 역할 |
|---|---|
| `SearchPanel` | 검색어, 자치구 필터, 상태 필터, 태그 필터 |
| `DongList` | 동 목록과 선택 상태 |
| `DongListItem` | 동 요약 카드 |
| `PredictionCard` | 추정 변화율, 추정 구간, coverage 안내 |
| `ComparisonCard` | 서울·자치구·동 비교 |
| `FactsPanel` | 전세·공급·정비사업·규제 사실정보 |
| `ComplexList` | 단지 목록과 최근 거래 |
| `EmptyState` | 선택 전, 검색 결과 없음, 예측 미제공 |
| `MapPanel` | 2차 구현. Kakao 지도 또는 좌표 폴백 |

## 6. 화면 문구 규칙

화면 문구는 예측을 작게 말하고, 사용자가 오해할 표현을 피한다.

| 상황 | 권장 문구 |
|---|---|
| 예측 제공 | `향후 12개월 추정 변화율 +3.2%` |
| 구간 표시 | `추정 구간 -4.1% ~ +10.9%, 기준 2026년 2분기` |
| coverage 안내 | `과거 검증에서 실제 변화율이 추정 구간 안에 든 비율은 약 64%입니다.` |
| 표본 부족 | `최근 1년 매매가 적어 예측하지 않음` |
| 선택 전 | `동을 검색하거나 목록에서 선택하세요.` |
| 결과 없음 | `검색 조건에 맞는 동이 없습니다.` |

금지 표현:

```text
저평가
고평가
적정가
유망
추천
투자 적격
매수 타이밍
80% 보장
재건축으로 오른다
```

## 7. 상태와 색상

색상은 `frontend-reproduce.md`의 토큰을 따른다.
상승·하락을 강한 빨강/파랑으로 과도하게 나누지 않고, 선택과 상태 구분에 집중한다.

| 상태 | 표현 |
|---|---|
| 선택됨 | primary border, 약한 배경, focus ring |
| 예측 제공 | `PREDICTED` badge, 기본 카드 |
| 표본 부족 | neutral badge, 변화율 대신 사유 표시 |
| 모델 미제공 | neutral badge, 사실정보만 표시 |
| 오류 | 강한 경고색보다 문장과 재시도 버튼으로 안내 |

변화율 숫자는 부호를 표시하되, 색 하나로 투자 매력처럼 보이게 하지 않는다.

## 8. 반응형 UX

| 환경 | 설계 |
|---|---|
| desktop | 좌측 검색·목록, 우측 상세. 상세는 sticky로 두어 선택 변경 시 바로 비교한다 |
| tablet | 검색, 목록, 상세를 세로로 쌓고 상세로 자동 스크롤한다 |
| mobile | 검색을 최상단에 두고, 목록 카드는 한 화면에 2~3개 정도 보이게 압축한다 |

모바일에서는 지도보다 목록과 상세 읽기가 중요하다.
지도는 2차 구현에서 접기 가능한 섹션으로 둔다.

## 9. 구현 단계

### 1단계: 프로젝트 골격

- `front/`에 Next.js 앱을 만든다.
- Tailwind CSS v4와 테마 토큰을 적용한다.
- `Button`, `Card`, `Badge`, `Input`, `SectionHeading`, `cn()`을 만든다.
- 샘플 데이터로 첫 화면 레이아웃을 확인한다.

완료 기준:

- `npm run build`가 통과한다.
- desktop, mobile에서 레이아웃이 겹치지 않는다.

### 2단계: 목록·상세 MVP

- 동 목록 데이터 타입을 정의한다.
- 검색어, 자치구 필터, 예측 상태 필터를 구현한다.
- 동 선택 상태를 URL query 또는 클라이언트 state로 관리한다.
- 선택 동 상세에 예측 카드와 사실정보 카드를 표시한다.

완료 기준:

- 사용자가 동을 검색하고 선택할 수 있다.
- `PREDICTED`, `INSUFFICIENT_SALES`, `NOT_SERVED` 상태가 모두 자연스럽게 보인다.
- 예측 문구에 금지 표현이 없다.

### 3단계: 비교와 지역 태그

- 서울·자치구·동 비교 카드를 추가한다.
- 규칙 기반 지역 유형 태그를 표시한다.
- 태그 필터를 목록에 연결한다.

완료 기준:

- 순위표 없이도 선택 동의 상대적 위치를 이해할 수 있다.
- 태그가 좋고 나쁨을 암시하지 않는다.

### 4단계: 실제 데이터 연결

- 정적 JSON 또는 API 중 선택한 방식으로 active snapshot 데이터를 연결한다.
- loading, empty, error 상태를 만든다.
- 데이터 누락 시 카드가 깨지지 않도록 fallback을 둔다.

완료 기준:

- 실제 데이터로 300개 안팎의 동 목록이 부드럽게 동작한다.
- 예측 미제공 동도 숨기지 않고 표시한다.

### 5단계: 지도 확장

- 법정동 경계 GeoJSON 또는 좌표 기반 폴백 중 가능한 방식을 확정한다.
- Kakao SDK는 클라이언트에서만 로드한다.
- SDK 키가 없거나 로드 실패하면 좌표 미리보기 또는 목록 화면으로 폴백한다.
- 지도 마커는 실제 `button`으로 만들어 접근성을 유지한다.

완료 기준:

- Kakao 키가 없어도 화면이 비지 않는다.
- 마커 클릭, 선택 이동, 모바일 접힘 상태가 정상 동작한다.

## 11. 우선 결정 사항

1. 첫 구현 데이터는 정적 JSON으로 갈지, API가 DB를 직접 읽게 할지 정한다.
2. `docs/payload-schema.md`에 비교값과 지역 태그 필드를 추가할지 정한다.
3. 지도 없는 MVP를 먼저 배포 가능한 범위로 인정할지 정한다.
4. 예측 미제공 동의 목록·지도 상태 표현을 확정한다.
5. Kakao 지도는 1차 출시 이후로 둘지, 개발 중 feature flag로 숨길지 정한다.
