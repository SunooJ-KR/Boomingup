# 제품 기획 정리 (초안)

> 상태: 초안 (2026-09-16). 팀 회의에서 나온 기획 방향을 제품 화면과 구현 단위로 다시 정리한다.
> 이 문서는 확정 결정이 아니다. 여기서 합의된 항목만 `docs/decisions.md`에 번호를 붙여 옮긴다.

## 1. 대상 사용자와 제공 가치

| 항목 | 내용 |
|---|---|
| 1차 대상 | 서울 아파트 매매를 검토하는 개인 투자자. 실거주 목적 사용자는 1차 대상이 아니지만, 지역 흐름 확인 용도로는 쓸 수 있다 |
| 핵심 질문 | "내가 보는 동네가 서울 전체 흐름과 비교해 어떤 위치에 있고, 향후 12개월 변화 폭은 어느 정도로 추정되는가" |
| 제공 형태 | 법정동 단위 12개월 추정 변화율, 추정 구간, 과거 검증 성능, 지역을 설명하는 사실정보 |
| 제공하지 않는 것 | 매수·매도 추천, 적정가 판정, 특정 단지 투자 판단, 수익률 보장 |

제품의 역할은 "정답을 알려주는 것"이 아니라, 사용자가 지역을 비교할 때 볼 수 있는 **일관된 기준표**를 주는 것이다.
예측값은 판단의 출발점이고, 단지·거래·전세·공급·규제 정보가 그 판단을 보완한다.

### 표현 규칙과의 관계

기획 문장은 투자자를 대상으로 하지만, 결정 1은 **화면에 판단 표현을 쓰지 않는다**로 되어 있다.
두 문장은 충돌하지 않는다. 다음처럼 나눠서 쓴다.

- 제품의 **목적과 대상**은 투자 검토자다. 소개 문구에는 이 맥락을 쓸 수 있다.
- 화면의 **수치와 문장**은 사실과 추정치만 쓴다. "추정", "구간", "기준 분기", "과거 검증 결과"를 함께 보여준다.
- 계속 금지: 저평가/고평가/적정가/유망/추천/투자 적격, "80% 보장", 특정 단지를 사라는 뜻으로 읽히는 문장.

쓸 수 있는 문장:

```text
향후 12개월 추정 변화율 +3.2%
추정 구간 -4.1% ~ +10.9%, 기준 2026년 2분기
과거 검증에서 실제 변화율이 추정 구간 안에 든 비율은 약 64%입니다.
```

쓰지 않는 문장:

```text
지금이 매수 타이밍입니다.
저평가된 지역입니다.
재건축 때문에 더 오를 가능성이 높습니다.
```

## 2. 기획 원칙

| 원칙 | 적용 방식 |
|---|---|
| 예측은 작게 말한다 | 예측값보다 기준 분기, 추정 구간, 검증 성능을 같이 보여준다 |
| 순위 경쟁을 줄인다 | 동 전체 랭킹보다 선택한 동의 변화율, 서울·자치구와의 비교, 표본 수를 먼저 보여준다 |
| 설명 가능한 정보부터 붙인다 | 새 데이터를 수집하기보다 이미 있는 거래·전세·공급·규제·정비사업 정보를 재사용한다 |
| 구현 가능한 화면부터 낸다 | 지도 경계 데이터가 막히면 목록·검색·상세 화면으로 먼저 검증한다 |
| 법적·윤리적 오해를 피한다 | 투자 조언처럼 읽히는 문구와 색상 강조를 피하고, 데이터 한계를 고정 노출한다 |

## 3. 사용자 흐름

MVP는 다음 흐름이면 충분하다.

1. 사용자가 법정동 또는 자치구를 검색한다.
2. 목록에서 동을 고른다.
3. 동 상세에서 12개월 추정 변화율, 추정 구간, 최근 1년 거래 수, 서울·자치구 대비 위치를 본다.
4. 같은 화면에서 전세가율, 정비사업 구역 수, 최근 준공 물량, 규제 여부 같은 사실정보를 확인한다.
5. 예측이 제공되지 않는 동은 이유를 본다. 예: "최근 1년 매매가 적어 예측하지 않음".

지도는 좋은 탐색 방식이지만, 법정동 경계 GeoJSON이 아직 없으므로 MVP의 필수 조건으로 두지 않는다.
초기에는 검색 가능한 목록과 상세 화면으로도 제품 가치를 확인할 수 있다.

## 4. 기획 항목별 현재 상태

### 4.1 지역 상승 폭 예측

| 항목 | 상태 |
|---|---|
| 예측 단위 | 법정동 (`sggCd` + `umdNm`, 결정 4) |
| 예측 기간 | 12개월 기본 (결정 11·16) |
| 모델 | 동×분기 hedonic 지수 + LightGBM, rolling-origin OOT로 검증 완료 |
| 검증 결과 | h=4 기준 MAE 0.0917, baseline B2(0.1018) 대비 약 10% 낮음 |
| 화면 상태 | 아직 구현 전. payload 스키마도 초안 |

기획에서 같이 가져가야 할 한계는 두 가지다.

1. **추정 구간이 목표만큼 정확하지 않다.** 과거 검증에서 실제값이 구간 안에 든 비율은 12개월 기준 64%다.
   시장 흐름이 바뀌는 해(2017·2021·2022)에는 31~34%까지 떨어졌다. 결정 17에 따라 이 수치를 화면에 같이 공개한다.
2. **동별 차이를 맞히는 힘은 제한적이다.** 서울 전체 평균 흐름을 미리 아는 가상의 기준값(0.0459)과 모델 MAE(0.0917)의 차이가 크다.
   따라서 "가장 많이 오를 동 TOP 10"처럼 순위를 강하게 내세우는 화면은 현재 모델의 한계를 넘는 인상을 준다.

권고 화면:

- 동 상세의 첫 줄은 `추정 변화율`, `추정 구간`, `최근 1년 매매 건수`로 구성한다.
- 그 아래에 `서울 전체`, `자치구`, `선택 동`의 과거 변화 흐름을 같이 보여준다.
- 정렬 기능은 두되, 기본 화면은 순위표보다 검색·필터 중심으로 둔다.

### 4.2 전체/부분 분석

기획 문장의 "전체/부분"은 먼저 지역 범위로 해석하는 편이 가장 현실적이다.

| 구분 방식 | 뜻 | 지금 가능한가 | 권고 |
|---|---|---|---|
| A. 지역 범위 | 서울 전체 → 자치구 → 법정동 | 가능하다. 현재 모형과 산출물 흐름에 가장 가깝다 | 1차 구현 |
| B. 주택 세부 구간 | 같은 동 안에서 면적대·층·연식별 가격 | 과거 실적 조회는 가능하다. 세부 구간 예측은 표본 부족 위험이 크다 | 2차 구현 |
| C. 가격대 | 동 안의 상위가·중위가·하위가 대역 | 계산은 가능하지만 표본이 적은 동에서 크게 흔들린다 | 보류 |

1차 구현은 A로 잡는다.
화면에서는 "서울 전체 흐름", "자치구 흐름", "선택 동 흐름"을 나란히 보여준다.
정밀한 기여도 분해까지 첫 버전에 넣을 필요는 없다. 먼저 같은 기준의 변화율을 비교해도 사용자는 선택한 동이 전체 흐름과 얼마나 다른지 이해할 수 있다.

B는 예측이 아니라 **과거 실적 조회**로 시작한다.
예: 선택한 동의 면적대별 최근 거래 가격 범위, 층 구간별 거래 수.
면적대별 향후 예측은 동 단위 예측보다 표본이 더 줄어드므로 첫 버전에서는 하지 않는다.

C는 당장 하지 않는다.

### 4.3 지역 유형 태그

기존 표현인 "클러스터링과 성향 분석"은 제품 기능으로 바로 약속하기에는 크다.
첫 버전에서는 **지역 유형 태그**로 낮춰 잡는다.

목적은 "이 동은 어떤 관측 특징을 가진 동네인가"를 짧게 설명하는 것이다.
가격이 얼마나 오를지와 별개로, 사용자가 자기 기준에 맞는 지역을 좁히는 데 쓴다.

입력 후보는 이미 만들어 둔 feature를 재사용한다. 새로 수집할 데이터는 두지 않는다.

| 묶음 | 예 | 사용 방식 |
|---|---|---|
| 가격 수준·변동성 | 동 지수 수준, 과거 변동 폭 | 상세 설명, 필터 |
| 거래 활발도 | 분기별 매매 건수, 최근 1년 표본 수 | 예측 신뢰 맥락, 필터 |
| 전세 구조 | 전세가율과 그 변화 | 상세 설명 |
| 공급·정비사업 | 준공 가구 수, 구역 단계별 개수 | 사실정보 태그 |
| 규제 | 투기과열지구 여부 | 사실정보 태그 |

첫 구현은 k-means보다 규칙 기반 태그가 안전하다.

예:

- `거래 많은 동`: 최근 1년 매매 건수가 서비스 대상 동 중 상위 30%
- `전세가율 높은 동`: 전세가율이 서비스 대상 동 중 상위 30%
- `정비사업 정보 있음`: 정비사업 구역 수가 1개 이상
- `최근 준공 많음`: 최근 8분기 준공 가구 수가 상위 30%

태그 이름은 좋고 나쁨을 담지 않는다.
"안정형", "성장형", "저평가형" 같은 이름은 쓰지 않고, "거래 많은 동", "전세가율 높은 동"처럼 관측된 특징만 쓴다.

k-means 같은 군집화는 이후 탐색 기능으로 검토한다.
쓴다면 표준화 후 5~7개 유형을 만들고 사람이 읽을 설명을 붙이되, 결정 18에 따라 **탐색적 결과**로 표시한다.
군집 결과를 예측 모델 feature로 되먹이지 않는다.

## 5. MVP 범위

첫 버전의 목표는 "실제 사용자가 동을 검색하고, 예측값과 사실정보를 한 화면에서 이해할 수 있는가"를 확인하는 것이다.

| 포함 | 제외 |
|---|---|
| 법정동 검색과 목록 | 매수·매도 추천 |
| 동 상세 예측 카드 | 동 전체 랭킹 중심 화면 |
| 추정 구간과 과거 coverage 안내 | "80% 보장" 같은 보장 문구 |
| 최근 1년 매매 건수와 예측 미제공 사유 | 표본이 부족한 세부 구간 예측 |
| 서울·자치구·동 비교 | 가격대별 예측 |
| 전세·공급·정비사업·규제 사실정보 | 새 외부 데이터 수집이 필요한 기능 |
| 규칙 기반 지역 유형 태그 | 자동 투자 성향 진단 |

## 6. 우선순위 제안

| 순서 | 할 일 | 이유 |
|---|---|---|
| 1 | DB에서 active snapshot을 읽어 동 목록·상세에 필요한 최소 payload를 만든다 | 화면 구현 전에 데이터 계약을 고정해야 한다 |
| 2 | 지도 없이 검색·목록·상세 MVP를 만든다 | 법정동 경계 GeoJSON이 없어도 제품 가치를 검증할 수 있다 |
| 3 | 동별 12개월 추정치, 추정 구간, coverage 안내를 상세 화면에 표시한다 | 이미 검증까지 끝난 핵심 산출물이다 |
| 4 | 서울·자치구·동 비교를 붙인다 | 새 모델 없이 비교 맥락을 줄 수 있다 |
| 5 | 규칙 기반 지역 유형 태그와 필터를 붙인다 | 새 데이터 없이 탐색성을 높일 수 있다 |
| 6 | 법정동 경계 GeoJSON을 확보한 뒤 지도 화면을 붙인다 | 지도는 유용하지만 현재는 데이터 의존성이 있다 |
| 7 | 면적대별 과거 실적 조회를 붙인다 | 예측이 아니라 조회로 시작하면 표본 문제를 피할 수 있다 |

## 7. 아직 막힌 것

| 항목 | 내용 |
|---|---|
| 법정동 경계 GeoJSON | 지도에 동을 색칠하려면 필요하다. 다만 목록·상세 MVP의 blocker는 아니다 (`docs/payload-schema.md` §6) |
| `front/` 비어 있음 | 저장소의 `front/`에 코드가 없다. `docs/front/frontend-reproduce.md`는 다른 프로젝트 화면을 기준으로 쓴 이식 가이드다 |
| payload 스키마 미합의 | `docs/payload-schema.md`가 아직 초안이다. 서울·자치구·동 비교와 지역 유형 태그를 넣으면 필드가 늘어난다 |
| DB 적재 스크립트 부재 | 스키마 정의와 적재 절차가 저장소에 없다 (`docs/railway-postgres-onboarding.md` §6) |
| 문구 검수 필요 | 투자 조언처럼 읽히는 표현을 막으려면 화면 문구 목록을 별도로 검수해야 한다 |

## 8. 결정이 필요한 질문

1. "전체/부분 분석"의 1차 의미를 서울·자치구·법정동 비교로 확정할 것인가.
2. 지도 없는 검색·목록·상세 MVP를 먼저 만들 것인가.
3. 지역 유형은 첫 버전에서 규칙 기반 태그로 시작해도 되는가.
4. 예측을 제공하지 못하는 동(직전 4분기 매매 20건 미만)을 목록과 지도에서 어떤 색·상태로 보일 것인가.
5. payload를 정적 JSON으로 먼저 만들지, API가 DB에서 바로 읽게 할지 결정할 것인가.
